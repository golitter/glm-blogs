# 相同query多次询问后不调用工具

在agent测试中，发现，输入相同的query，多次后就不调用对应工具了，而是直接给出结果，开始给出虚拟的信息。无论怎么调整提示词都不可以。

后来发现是llm提供商那里有对话缓存机制，当使用相同的query时，系统会先检查缓存，如果命中就返回缓存的答案。

还有就是模型的“惰性”

几次相同的`query-answer`后，模型产生了“惰性”，而不会采样设计的提示词规则。

对话历史变长之后，系统提示词的权重在模型的“注意力”权重会被稀释，可能导致模型忽略了工具调用这一步（在实际测试中，感觉还是上面两条ok，可能目前历史总token没达到一定长度

# 模型供应商、vllm的缓存有什么区别

> 既然模型供应商的缓存会有这样的影响，那么vllm这些有KVcache的是不是也会有这样的影响？
>
> >  下面是由chatglm协助给出

## 应用层缓存

**跨多次API调用或对话会话。**节省计算资源和API调用成本。如果你问了同一个问题，系统直接返回上次缓存好的答案，而不再重新走一遍“分析-调用工具-生成”的流程。

## KVCache

**单次API调用内部的生成过程。**加速文本生成。LLM生成文本是逐个token进行的。KV Cache存储了已经生成过的token的“状态”（键和值），这样在生成下一个token时，就不需要重新计算之前所有token的上下文关系，只需关注新的token即可。

KV Cache本身**不会**像应用层缓存那样，直接“复用”上一次完整问答的结果。每次发送一个新的请求（即使是相同的query），VLLM通常会启动一个新的推理过程，KV Cache也是从这个新请求开始计算的。

**但是会加速应用层缓存的作用**。



基于此，我找到了deepseek的应用层缓存描述 “**硬盘缓存只匹配到用户输入的前缀部分，输出仍然是通过计算推理得到的。**” 

这里：**应用层缓存让模型跳过了重新读取和理解系统提示词**，直接进入“生成回答”的阶段。

**当它能以极快的速度进入决策阶段时，它更有可能根据记忆中的模式直接生成文本，而不是严格执行“分析-调用工具”的复杂流程。缓存没有让它跳过工具调用，而是让它“懒得”去调用工具，并更快地生成了虚构内容。**
