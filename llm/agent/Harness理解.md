# 2026年的关键转折：从拼模型到拼harness

现如今，llm能力已经非常强了，可以应对绝大部分常规任务。现在比拼的是harness。

> 将llm固定不动，只换harness、模型的外围，性能就能产生巨大的差异。

通过harness，尽可能控制agent的输入结果。



设计模式：抽象能力加上结构化，把很乱的东西的本质找到。

30年软件工程史，本质就是用“抽象”不断驯服升维复杂度的历史——从对象、架构、分布式一路演进到数据。但前30年，我们驾驭的全是**“确定性”系统**；而Agent时代，首次引入了**“不确定性”的概率机器**。Harness的出现并非偶然，它是工程演进到此刻必然诞生的新抽象，是驾驭Agent这匹野马的“缰绳”。

> 来自 chatglm



agent工程三次变革：

- `Prompt Engineering`：向llm输入恰当提示词让模型回答的更恰当。可能会用到提示词技巧、COT等。
- `Context Engineering`：基于“输入深度怎么样，输出深度就怎么样“，本质上就是在有限上下文中尽可能塞入更恰当的数据，例如RAG等。
- `Harness Engineering`：只关注与Context有局限性，模型的能力更加强大，不仅仅用来回答问题，还要自动完成任务。基于“自动”做**可控管理**，设计可控的系统。

> 第一阶段主要用于QA，workflow中嵌入的llm节点。
>
> 第二阶段主要用于QA、tool-use agent。agent也是基于上下文内容进行loop。
>
> 第三阶段跟第二阶段有很大交集，只是模型更加强大还有openclaw的火起来出来的新概念？。虽然有很大交集，但是侧重点还是不同的，感觉是马和马鞍区别。第二阶段的agent相当于马，主要在上下文；第三阶段相当于马鞍，主要在于如何控制模型，使其输出“可控”（如何驾驭模型？）



这三个都是为了解决上下文推理失控问题而提出的，循序渐进，可能并非是一个新概念就可以定义的。

```shell
Agent = Model + Harness
```

Harness就是包裹模型运行的基础设施，所有的外围工具都是Harness。

Harness 就是运行时和基础设施，大家可以把它简单理解为一个模型运行时、Agent 自助工具系统，然后上下文管理、权限控制、状态持久化，所有的东西都是 Harness 要解决的。

> 很多东西在Context阶段也有。
>
> 感觉：**Context阶段主要是上下文设计系统，Harness阶段在于模型外围设计系统**。

**Harness 做的就是把大模型的大脑变成了 Agent 的身体。**

> Context阶段是将大模型作为agent大脑，类似于一个人形机器人，大模型上下文是大脑，其他是类似人性机器人的手脚，可以像人一样操作处理。
>
> Harness阶段是将大模型大脑为一个“agent”，不是人形机器人，这个大模型大脑要比模型上下文作为大脑更加复杂。

Harness的核心组件：

- `Agentic Loop`：输入到输出之间的一个详细循环过程。复杂行为执行都是在这个loop中，类似于reAct架构。
- `Tool System`：工具调用能力。
- `Memory & Context Management`：记忆和上下文管理。
- `Guardrails`：权限管理。
- `Hooks`：钩子。
- `Session`：会话的连续性。

> Guardrails-权限管理，防止agent干坏事蠢事，有时在执行指令前需要像用户进行确认。动态的。
>
> Hooks-钩子：流程中绝对不能发生的事情。是静态的。



Anthropic提出“Harness随时可抛弃”的观点：现在Harness本质傻姑娘是补偿大模型缺陷的“拐杖”，但是随着模型能力提升，这些曾经的解法必定会成为agent累赘。因此，不能把当下控制流写死在系统中，而应该将harness设计为轻量、可替换的抽象层，只在架构中沉淀业务规则与安全边界这些“不变量”，保持对底层执行引擎随时“换拐杖”甚至“扔拐杖”的解耦能力。





agent时代，工程师的核心不在于写代码，而在于：

- 理解系统的复杂性
- 抽象和结构化思维
- 驾驭不确定性
