# 背景

qwen3-32b不支持`json schema`结构化输出，qwen3.5-27b/35b支持。

qwen3-32b是采用提示词注入json规范来提取json，qwen3.5则可以采用respose_format="json_schema"来进行提取。

同时，qwen3的json不保证百分百，而qwen3.5则是百分百json，但是字段提取效果差。

基于此，统一llm参数统一节点。

同时，实验发现：

- qwen3的指令遵循要比qwen3.5要强，同样的提示词qwen3可以得到正确结果，qwen3.5不能。可能原因：预训练语料库不同、模型不同，该提示词适用于qwen3，没有特化为qwen3.5
- `json_schema`要求**一级字段**必须为`required`，但是实践中的json schema是多级嵌套的，required不行。
- 项目中的存在问题：对于嵌套字段，若整个为null，则不显示，否则会报错，与**qwen3系列产生了耦合**，对新模型（qwen3.5）不友好。

# dify实现

dify中，如果模型不支持`json_schema`，则使用提示词注入，之后结构化提取，采用`json_repair`库。

注意到，无论模型是否支持`json_schema`，结构化提取都要进行结构化函数进行提取。

结构化函数主要使用的是`json_repair`库来进行修复。

> json_repair库：主要处理llm输出json的失败处理。

## 调研

**选用json schema**：

1. 提示词注入方式有不确定风险，存在复现难，随机性高（还有kvcache等）。`json_schema`尽管存在参数提取性能下降，但是可以保证百分百正确json格式，**百分百准确率最重要**。
2. 参数提取性能下降（相比提示词注入方式）可以在后期使用微调来缓解。更重要的是**服务端可以进行调整来适配**，这样保证了项目节点的通用性！！
3. 部分开源模型不提供`json_schema`的输出方式，但是主要推理框架可以支持`json_schema`。



目前json schema的缺点：

1. 一级字段必须是required
2. 缺乏范围、字符长度、数组长度限制等。
