# 后端测试分层与压测

接口调通只能说明单次请求能返回，真正的后端要扛并发、慢请求、连接池压力、代码改动和偶发错误。测试是分层的安全网：单元测逻辑、接口测 HTTP、压测看压力、race 测并发，不要指望一种工具解决所有问题。

---

## 测试金字塔

越往上越贵、越慢，数量越少：

```
       /\
      /E2E\        真实链路（少量）
     /------\
    /  集成  \     handler + 真实依赖
   /----------\
  /    单元    \   纯业务逻辑（最多）
 /--------------\
```

| 层次 | 解决的问题 | 常用工具 |
| ---- | ---- | ---- |
| 单元测试 | 业务逻辑是否正确 | `go test` / pytest / JUnit |
| Handler 测试 | 路由、参数、响应 | `httptest` / MockMvc |
| 接口调试 | 真实 HTTP 是否可用 | curl / Postman / Apifox |
| 单接口压测 | 吞吐、延迟、错误率 | `hey` / `wrk` |
| 流程压测 | 登录鉴权 + 读写混合 | `Locust` / `k6` |
| 并发安全 | 是否有数据竞争 | `go test -race` |

接口工具负责调试，压测工具负责观察压力，自动化测试负责守住逻辑。

---

## 单元测试

测小而清晰的规则，**不碰真实数据库 / 第三方**，用 fake / stub / mock 隔离依赖。

典型覆盖点：

- 必填字段为空是否报错
- 边界参数是否被限制
- 默认值是否正确
- 依赖层返回错误时是否正确处理
- 权限 / 归属关系是否符合预期

价值在**重构时快速知道有没有破坏既有行为**。

---

## 接口测试

接近真实调用，主要查：路由、请求体解析、参数校验、鉴权、状态码、响应结构稳定性。

| 工具 | 适合场景 |
| ---- | ---- |
| curl | 快速验证、写文档示例 |
| Postman | 个人调试、集合管理 |
| Apifox | 接口文档、Mock、团队协作 |
| REST Client / HTTPie | 文本化请求，适合进仓库 |

**不要只测成功路径**。参数缺失、格式错误、未授权、资源不存在等失败路径同样要覆盖。

---

## 压测指标：看 P95 / P99，别只看平均值

平均值会骗人：

```
平均延迟：20ms
P99：2s
```

大多数请求很快，但仍有少量用户遇到非常慢的请求。调用量大时这些慢请求每天真实发生。压测时**至少看 P95 和 P99**，它们更接近压力下的真实体验。

核心指标速查：

| 指标 | 含义 | 关注点 |
| ---- | ---- | ---- |
| `Requests/sec` | 吞吐量 | 同等并发下越高越好 |
| 平均延迟 | 粗略体感 | 容易被尾部拉偏 |
| P95 / P99 | 尾部延迟 | 真实用户体验下限 |
| 状态码分布 | 错误率 | **第一目标 = 0 错误** |
| 超时数 | 压力边界 | 找到压力开始不稳定的并发点 |

RPS 高但错误率也高，不是性能好，是服务被打坏了。先保证错误率为 0，再逐步加并发。

---

## hey

最轻量，适合回答「这个接口在固定并发下表现怎样」。

```bash
hey -n <总请求数> -c <并发数> <接口地址>
# 例：1 万请求、50 并发
hey -n 10000 -c 50 http://localhost:8080/api/users
```

看 `Requests/sec`、平均延迟、P95 / P99、状态码分布、是否超时。

---

## Locust

`hey` 适合单接口，`Locust` 适合完整流程：进入系统 → 鉴权 → 查询 → 写入 → 再查询。这类流程用 Python 写很自然。

```bash
conda create -n loadtest python=3.11
conda activate loadtest
pip install locust

locust -f <压测脚本> --host <服务地址>
```

优势：自动登录鉴权、任务执行权重、多类用户行为、Web UI 实时观察、结果可导出对比。

---

## 压测工具怎么选

| 工具 | 特点 | 适合场景 |
| ---- | ---- | ---- |
| `hey` | 最轻量，一条命令开压 | 学习压测、快速测单接口 |
| `wrk` | 性能强，支持脚本扩展 | 高性能 HTTP 压测 |
| `k6` | 脚本化、CI 友好 | 现代 API 压测 |
| `Locust` | Python 描述用户行为 | 真实业务流程压测 |
| `JMeter` | GUI、多协议、报告成熟 | 企业级 / 正式性能测试 |
| `Gatling` | 场景 DSL、报告漂亮 | 正式性能测试场景 |

学习顺序保持轻量：

```
接口调试 → 单元测试 → hey → Locust / k6 → 并发检测
```

`JMeter` 很强，但更适合正式性能测试或已有测试团队维护。个人学习和后端自测，`hey` 和 `Locust` 更顺手。

---

## 并发安全：`go test -race`

数据竞争在普通单测里很难暴露，靠 `-race` 检测器在运行期抓共享变量的非同步访问。

```bash
go test -race ./...
```

发现竞争会打印两处访问的堆栈。Go 里 race 检测器是 CI 常驻项，竞争一旦上线是难复现的偶发 bug。

---

## 数据库连接池

大多数服务通过连接池访问 DB，连接池既影响吞吐，也保护 DB 不被瞬间打爆。压测时盯住：

- 请求是否大量超时
- 日志是否出现 DB 连接错误
- P95 / P99 是否突然飙升
- DB 是否连接数过多
- 写接口是否拖慢读接口

压测的目的不是把 DB 打爆，而是找到系统性能开始恶化的并发点。

---

## 写接口压测要隔离数据

写接口会真实产生数据，必须隔离：

- 用专门的测试账号 / 测试租户
- 不用日常开发账号压测
- 不把密钥、凭证、密码写进文档
- 压测后清理测试数据
- 不直接压生产数据库

测试数据和正常数据分开，是很朴素但必须的工程习惯。

---

## 压测结果该记录什么

| 项 | 示例 |
| ---- | ---- |
| 测试环境 | 本地 / 预发，机器规格 |
| 数据规模 | 表行数、数据量级 |
| 压测命令 / 脚本版本 | `hey -n 10000 -c 50 ...` |
| 并发数 | 50 |
| RPS | 1200 |
| 平均延迟 | 20ms |
| P95 / P99 | 80ms / 2s |
| 状态码分布 | 200: 9990, 500: 10 |
| 错误 / 异常观察 | 超时 0、DB 连接错误 10 |

**不要记录任何敏感信息。**

---

## 总结

- 单元测试保证业务逻辑，不碰真实依赖。
- 接口测试保证 HTTP 行为，覆盖成功和失败路径。
- 压测看 P95 / P99 和错误率，错误率为 0 是第一目标。
- `hey` 测单接口，`Locust` 模拟真实用户流程。
- `go test -race` 检测并发数据竞争。
- 压测数据要隔离，不压生产、不记敏感信息。
