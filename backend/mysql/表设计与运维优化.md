# 表设计与运维优化

---

## 三大范式

| 范式 | 核心规则 | 解决的问题 |
|------|----------|-----------|
| 1NF | 字段不可再分，每列都是原子值 | 消除复合字段 |
| 2NF | 在 1NF 基础上，非主键字段完全依赖主键（消除部分依赖） | 联合主键中某列只依赖部分主键 |
| 3NF | 在 2NF 基础上，非主键字段不传递依赖主键 | A→B→C 的间接依赖 |

---

## 反范式

- 范式导致表拆得太细，查询需要大量 JOIN，性能差
- 反范式：适当增加冗余字段，减少 JOIN 次数
- 什么时候可以冗余：读多写少的字段、对一致性要求不高的字段
- 什么时候不要冗余：写多读少的字段、数据一致性要求高的字段
- 实际做法：先按第三范式设计，遇到性能问题再针对性反范式优化

## 字段类型选择

### 整数类型

| 类型 | 字节 | 适用场景 |
|------|------|----------|
| TINYINT | 1 | 状态、枚举（性别、订单状态） |
| INT | 4 | 自增主键、外键 |
| BIGINT | 8 | 数据量大时的主键 |

- 够用就行，不要什么都用 BIGINT（浪费索引空间）

### 字符串类型

| 类型 | 适用场景 |
|------|----------|
| CHAR(N) | 长度固定（手机号、MD5） |
| VARCHAR(N) | 长度不固定（姓名、地址），N 设合理上限 |
| TEXT | 大段文本，尽量少用（不能设默认值、索引受限） |

- 不要用 VARCHAR 存需要参与运算的数字

### 时间类型

| 类型 | 字节 | 适用场景 |
|------|------|----------|
| DATETIME | 8 | 业务时间（创建时间、更新时间），推荐 |
| TIMESTAMP | 4 | 需要时区转换的场景，有 2038 限制 |

- 不要用 VARCHAR 存时间（无法用时间函数、比较慢）

### 金额

- 涉及钱的**必须用 DECIMAL**，FLOAT/DOUBLE 有精度丢失（0.1 + 0.2 ≠ 0.3）

## 深分页优化

### 问题

`LIMIT 49990, 10` 会扫描 50000 行，丢弃前 49990 行，偏移量越大越慢。

### 三种优化方案

| 方案 | 做法 | 适用场景 |
|------|------|----------|
| 游标分页（推荐） | 记住上一页最后的 id，`WHERE id > 上次id ORDER BY id LIMIT 10` | App 无限滚动 |
| 子查询延迟关联 | `SELECT * FROM t JOIN (SELECT id FROM t LIMIT offset, size) tmp ON t.id=tmp.id` | Web 需要跳页 |
| 禁止深翻页 | 业务限制最多翻到第 N 页，加筛选条件缩小范围 | 通用 |

### 游标分页限制

- 只能上一页/下一页，不能跳到任意页
- 需要一个有序且唯一的列（通常是主键 id）

### 延迟关联原理

子查询走覆盖索引找到 10 个目标 id（不回表），主查询只对这 10 个 id 回表。原始写法回表 50000 次，优化后只回表 10 次。

## 慢查询日志与分析

### 开启慢查询

- `SET GLOBAL slow_query_log = ON`
- `SET GLOBAL long_query_time = 1`（超过 1 秒记录，默认 10 秒太大）
- 设置后需重新连接才能看到新值

### 分析工具

| 工具 | 说明 |
|------|------|
| 直接查看 slow.log | 看原始日志，含 Query_time、Rows_examined 等 |
| mysqldumpslow | MySQL 自带汇总工具，`-s t -t 10` 按时间取前 10 |
| pt-query-digest | Percona 工具，输出完整分析报告 |

### 排查流程

1. 从慢查询日志找到慢 SQL
2. EXPLAIN 分析执行计划
3. 重点关注：type=ALL（全表扫描）、key=NULL（没走索引）、Using filesort、Using temporary、rows 很大
4. 针对性优化：加索引、改写 SQL、调整业务逻辑

### 常用状态查看

- `SHOW PROCESSLIST`：当前连接和正在执行的 SQL
- `SHOW GLOBAL STATUS LIKE 'Slow_queries'`：慢查询数量
- `SHOW GLOBAL STATUS LIKE 'Threads_connected'`：当前连接数

## 备份与恢复

### mysqldump 逻辑备份

```bash
# 备份单库（推荐参数）
mysqldump -u root -p --single-transaction --routines --triggers db_name > backup.sql

# 恢复
mysql -u root -p db_name < backup.sql
```

- `--single-transaction`：InnoDB 一致性备份，不锁表（**必须加**）
- `--routines`：同时备份存储过程和函数
- `--triggers`：同时备份触发器（默认开启）

### PITR（基于时间点的恢复）

1. 恢复最近全量备份（mysqldump）
2. 用 mysqlbinlog 重做备份点到目标时间点的操作：

```bash
mysqlbinlog --start-datetime="时间1" --stop-datetime="时间2" binlog文件 | mysql -u root -p
```

- 按位置恢复更精确：`--start-position=N --stop-position=N`

## 主从复制搭建要点

### 复制三步骤

1. 主库写 Binlog
2. 从库 IO 线程拉取 Binlog → 存为 Relay Log（中继日志）
3. 从库 SQL 线程读取 Relay Log 并执行

### 关键配置

- 主库：`server-id=1`、`log-bin=mysql-bin`、`binlog-format=ROW`
- 从库：`server-id=2`（必须与主库不同）、`relay-log=relay-bin`、`read-only=ON`

### 复制方式

| 方式 | 命令 | 特点 |
|------|------|------|
| 传统复制 | `CHANGE MASTER TO MASTER_LOG_FILE=..., MASTER_LOG_POS=...` | 需要手动指定位置 |
| GTID 复制（推荐） | `CHANGE MASTER TO MASTER_AUTO_POSITION=1` | 自动找位置，切换方便 |

### 验证复制状态

```sql
SHOW SLAVE STATUS\G
-- Slave_IO_Running: Yes
-- Slave_SQL_Running: Yes
-- Seconds_Behind_Master: 0（延迟秒数）
```

- 两个 Running 都是 Yes 才正常
- `Seconds_Behind_Master` 增大说明从库在追数据

### Docker 搭建注意

- 两个容器需要在同一 Docker 网络中才能用容器名通信
- 主库端口映射 3307，从库映射 3308，避免与本地 MySQL 冲突

## 常见运维操作

### 用户与权限

- 权限最小原则：只给 SELECT/INSERT/UPDATE/DELETE，不给 DROP/ALTER/CREATE
- `CREATE USER` → `GRANT` → `FLUSH PRIVILEGES`
- `SHOW GRANTS FOR user` 查看权限

### 表维护

| 操作 | 命令 | 说明 |
|------|------|------|
| 查看表大小 | 查 information_schema.TABLES | DATA_LENGTH + INDEX_LENGTH |
| 优化表（回收碎片） | `OPTIMIZE TABLE t` | 重建表，**会锁表**，低峰期执行 |
| 分析表（更新统计） | `ANALYZE TABLE t` | 不锁表，帮优化器选对索引 |
| 检查表 | `CHECK TABLE t` | 检查表是否有错误 |

### 连接管理

- `SHOW PROCESSLIST`：查看所有连接
- `KILL id`：杀掉某个连接
- `Too many connections` → 增大 `max_connections` 或排查未释放的连接
