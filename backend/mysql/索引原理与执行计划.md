# 索引原理与执行计划

---

## 索引类型

| 类型 | 特点 | 数量限制 |
|------|------|----------|
| 主键索引（PRIMARY KEY） | 唯一 + 不允许 NULL，自带聚簇索引 | 每表只能 1 个 |
| 唯一索引（UNIQUE） | 唯一 + 允许 NULL（可多个 NULL） | 可多个 |
| 普通索引（INDEX） | 无唯一性约束 | 可多个 |
| 联合索引 | 多列组合索引，列的顺序关键 | 可多个 |

- `SHOW INDEX FROM 表名`：查看表上所有索引及其列、类型
- `DROP INDEX 索引名 ON 表名`：删除索引
- 有外键约束的列上索引不能直接删除，需先删外键

---

## B+ 树核心原理

- 非叶子节点只存 KEY，叶子节点存数据 → 树更矮，IO 更少
- 叶子节点形成有序双向链表 → 范围查询快
- 3 层 B+ 树可存约 10 亿条记录，2-3 次 IO 即可找到数据
- MySQL 选 B+ 树而非 B 树/红黑树/Hash：B 树非叶子存数据导致树更高，红黑树太高 IO 多， Hash 不支持范围查询和排序

### 主键选择

- 推荐用 `INT AUTO_INCREMENT` 或 `BIGINT AUTO_INCREMENT`
- 字符串主键（如 UUID）占用空间大、比较慢、无序插入导致页分裂

## 聚簇索引 vs 二级索引

| | 聚簇索引（主键） | 二级索引（非主键） |
|---|---|---|
| 叶子节点存什么 | 整行数据 | 索引列值 + 主键 id |
| 数量 | 每表 1 个 | 可多个 |
| 查整行数据 | 直接拿到，无需回表 | 需要回表（用主键 id 再查一次聚簇索引） |

### 回表

二级索引查到的数据不包含所需全部列时，用主键 id 去聚簇索引再查一次。走主键索引直接查不存在"回表"概念。

---

## 最左前缀匹配原则

联合索引 `(a, b, c)` 的 B+ 树按 a → b → c 依次排序。

| 查询条件 | 是否命中 | 用到哪些列 |
|----------|----------|-----------|
| `WHERE a = 1` | ✅ | a |
| `WHERE a = 1 AND b = 2` | ✅ | a, b |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ | a, b, c |
| `WHERE b = 2` | ❌ | 跳过了 a |
| `WHERE b = 2 AND c = 3` | ❌ | 跳过了 a |
| `WHERE a = 1 AND c = 3` | ✅ | 只用到 a，中间断了 b |

- MySQL 优化器会自动调整 WHERE 条件顺序，不需要按索引列顺序写
- 联合索引中的非首列不等于有单独索引，`WHERE salary > 10000` 在联合索引 `(dept_id, salary)` 上走不了索引

---

## 覆盖索引

查询所需的所有列都在索引中，不需要回表。

- 判断标志：EXPLAIN 的 Extra 列出现 `Using index`
- 实际开发中 `SELECT` 尽量只写需要的列，避免 `SELECT *`

## 索引失效场景

| 场景 | 示例 | 修复方式 |
|------|------|----------|
| 索引列使用函数 | `LEFT(name, 1) = '张'` | 改为 `name LIKE '张%'` |
| 索引列做运算 | `salary + 1000 > 15000` | 改为 `salary > 14000` |
| 隐式类型转换 | `name = 123`（name 是 VARCHAR） | 加引号 `name = '123'` |
| LIKE 以 % 开头 | `name LIKE '%张'` | 只有 `LIKE '张%'` 能走索引 |
| OR 连接非索引列 | `name = '张三' OR col = x`（col 无索引） | 给 OR 每个列都建索引 |
| != / <> / NOT IN | `name != '张三'` | 视数据分布，优化器可能放弃索引 |
| 联合索引不满足最左前缀 | 跳过第一列查第二列 | 按最左前缀写查询条件 |

- OR 两边都必须有索引，否则可能全表扫描

## EXPLAIN 执行计划

`EXPLAIN` 放在 SELECT 前面，不真正执行查询，只返回执行计划。

### type 字段（访问类型，从好到差）

```
system > const > eq_ref > ref > range > index > ALL
```

| 类型 | 含义 |
|------|------|
| system | 表中只有一行 |
| const | 主键/唯一索引等值查询，只返回一条 |
| eq_ref | JOIN 时被驱动表通过主键/唯一索引匹配 |
| ref | 非唯一索引等值查询 |
| range | 索引范围扫描（>、<、BETWEEN、IN） |
| index | 全索引扫描 |
| ALL | 全表扫描，必须优化 |

目标：至少达到 range 级别

### key 字段

- `possible_keys`：可能用到的索引
- `key`：实际用到的索引（NULL = 没走索引）

### Extra 字段

| 值 | 含义 |
|----|------|
| `Using index` | 覆盖索引，不回表 ✅ |
| `Using where` | Server 层过滤 |
| `Using index condition` | 索引下推（ICP） |
| `Using filesort` | 额外排序，需优化 ⚠️ |
| `Using temporary` | 使用临时表，需优化 ⚠️ |

- 回表是存储引擎的正常操作，不会在 Extra 中标注
- 只有覆盖索引（省了回表）才会标注 `Using index`

### 索引下推（ICP）

MySQL 5.6+ 优化，存储引擎在遍历索引时就根据 WHERE 条件过滤，减少回表次数。

## 索引设计建议

**该建索引：** WHERE/JOIN/ORDER BY/GROUP BY 频繁使用的列、区分度高的列

**不该建索引：** 小表、区分度低的列（如性别）、频繁更新的列、很少查询的列

**索引不是越多越好：** 占空间、增删改需维护、优化器选择耗时，建议每表不超过 5-6 个
