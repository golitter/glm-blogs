# 数据类型：重点摘要

---

## 大小写规则

| 项目 | 是否区分 |
|------|---------|
| 命令（SET/set） | 不区分 |
| 键（key） | **区分** |
| 值（value） | **区分** |

> **命令是给人看的，不区分；数据是给程序用的，必须区分。**
> `SET Name 1` 和 `SET name 1` 是**两个不同的键**。

---

## 命令命名规律

```
首字母 = 类型：S=Set, H=Hash, L=List, Z=ZSet
后面 = 英文单词缩写
```

| 命令 | 拆解 | 含义 |
|------|------|------|
| `SCARD` | **S**et + **CARD**inality | 统计元素个数 |
| `SISMEMBER` | **S**et + **IS MEMBER** | 判断元素是否在集合中 |
| `SINTER` | **S**et + **INTER**section | 交集 |
| `ZRANGE` / `ZREVRANGE` | **Z**Set + (**REV**erse) + **RANGE** | 升序/降序取范围 |
| `HGETALL` | **H**ash + **GET ALL** | 取所有字段 |

> 看到命令首字母就能猜出是哪种类型。

---

## 五种类型速记

```
String   →  缓存/计数器/分布式锁      (SDS, 512MB)
Hash     →  对象/单字段操作            (ziplist→hashtable)
List     →  队列/栈                   (quicklist, 注意方向!)
Set      →  去重/集合运算             (hashtable/intset)
ZSet     →  排行榜/带分排序           (skiplist+hashtable)
```

| 类型 | 有序? | 去重? | 底层结构 | 典型场景 |
|------|-------|-------|---------|---------|
| String | - | - | SDS | 缓存、计数器、分布式锁 |
| Hash | - | field 去重 | ziplist→hashtable | 对象存储 |
| List | ✅有序 | ❌可重复 | quicklist | 队列、栈 |
| Set | ❌无序 | ✅去重 | hashtable/intset | 共同好友、标签 |
| ZSet | ✅有序 | ✅去重 | skiplist+hashtable | 排行榜 |

## String

| 要点 | 说明 |
|------|------|
| 底层 | SDS（Simple Dynamic String） |
| 最大值 | 512MB |
| `EX` / `PX` | 秒级 / 毫秒级过期 |
| `NX` | 键**不存在**才设置（分布式锁基础） |
| `XX` | 键**已存在**才设置 |
| `INCR` | 原子递增，线程安全 |

### 为什么 INCR 是线程安全的？

**不是因为加锁，而是因为 Redis 单线程 + INCR 是单条命令。**

Redis 处理命令是单线程的，一次只执行一条，所以两条 INCR 不可能同时碰到同一个值——天然原子。

> ⚠️ **关键推论**：单线程只对**单条命令**成立。
> `GET` → 代码 `+1` → `SET` 是三条命令，中间会被插队，不安全。必须用 `INCR` 这种一条命令搞定的。

### SDS vs C 字符串（高频面试）

1. **O(1) 获取长度** —— SDS 头部有 len 字段；C 字符串要遍历到 `\0`（O(N)）
2. **二进制安全** —— SDS 用 len 判断结尾，能存图片/序列化数据；C 字符串遇 `\0` 会截断
3. **空间预分配 + 惰性释放** —— 减少内存重分配次数
4. **防缓冲区溢出** —— 拼接前检查空间

### NX 与分布式锁

```bash
SET lock:order:123 1 NX EX 10
```

`NX` 保证只有一个客户端能设置成功（抢到锁），`EX` 防死锁。**一条命令搞定"加锁+设过期"，是原子的**——如果分两条（先 SET 再 EXPIRE），中间崩溃会死锁。

**典型场景**：缓存、计数器、分布式锁、Session

## Hash

```
user:1  →  { name: "张三", age: 20, city: "北京" }
```

| 要点 | 说明 |
|------|------|
| 适合存 | 对象属性，单字段频繁读写 |
| 底层 | 小数据用 ziplist，大了转 hashtable |
| 删单字段 | `HDEL key field`，**必须指定字段名** |
| 删整个键 | 用 `DEL key`，不是 `HDEL` |

### 查看命令

| 命令 | 返回 |
|------|------|
| `HGET key field` | 单个字段的值 |
| `HGETALL key` | 所有字段名 + 值 |
| `HKEYS key` | 只返回所有字段名 |
| `HVALS key` | 只返回所有值 |
| `HLEN key` | 字段个数 |

### 底层编码转换（高频面试）

| 阶段 | 编码 | 特点 |
|------|------|------|
| 数据小 | **ziplist** | 省内存，查找 O(N) |
| 数据大 | **hashtable** | 查找 O(1)，内存占用大 |

**转换阈值**：field **> 512** 个 **或** 单个 value **> 64 字节**，满足任一即转 hashtable。
查看编码：`OBJECT ENCODING key`

> 设计思想：小数据用 ziplist 省内存（Redis 里小对象很多，省下来很可观）；大数据用 hashtable 保性能。

### HDEL vs DEL（易错点）

- `HDEL` = 删**字段**（Hash 内部的一个 field）→ **必须带 field**
- `DEL` = 删**整个 key**（连同所有字段）

```bash
HDEL user:1 name      # ✅ 删 name 字段
DEL  user:1           # ✅ 删整个 user:1
HDEL user:1           # ❌ 报错，缺 field
```

### Hash vs String 存 JSON

| 维度 | String 存 JSON | Hash |
|------|---------------|------|
| 改单字段 | 整个 JSON 读出→改→写回 | ✅ `HSET` 只动一个字段 |
| 读单字段 | 读整个 JSON 再解析 | ✅ `HGET` 直接取 |
| 内存 | 较大 | 较省（ziplist 压缩）|
| 字段单独过期 | 只能整个 key 过期 | ❌ 不能给单个 field 设过期 |

> 选型：字段**常单独读写** → Hash；**整体存取** → String 存 JSON 也行。

## List

| 要点 | 说明 |
|------|------|
| 底层 | quicklist（ziplist + 双向链表） |
| 有序、可重复 | |
| 队列 FIFO | `LPUSH` + `RPOP`（**进和出要在不同端**） |
| 栈 LIFO | `LPUSH` + `LPOP`（同端进出） |

### 经典易错点：队列方向

**核心：LPUSH 是从左边塞进去。**

```
LPUSH list A → [A]
LPUSH list B → [B, A]      (B 在左)
LPUSH list C → [C, B, A]   从左到右：C B A
```

- **LPUSH + LPOP（同端）= 栈 LIFO**：LPOP 出 C（最后塞的）→ 后进先出
- **LPUSH + RPOP（不同端）= 队列 FIFO**：RPOP 出 A（最早塞的）→ 先进先出

> **记忆**：进和出必须**不同端**才是队列。`L...R`（一左一右）= 队列；`L...L`（同一个 L）= 栈。

### List 做消息队列的局限

| 局限 | 说明 |
|------|------|
| ❌ 无 ACK | 取走后消费者崩溃，消息就丢了 |
| ❌ 无消费者组 | 不能像 Kafka 分组消费 |
| ❌ 消息不可回溯 | 取走就没，没法重消费 |

> 生产环境用 **Stream**（Redis 5.0+，支持消费者组和 ACK）或专业 MQ。

## Set

| 要点 | 说明 |
|------|------|
| 无序、去重 | 重复添加不会多存 |
| 底层 | hashtable 或 intset（全整数时） |
| `SISMEMBER` | 判断元素是否在集合中（O(1)）|
| `SCARD` | 统计元素个数 |
| 集合运算 | `SINTER`（交集）、`SDIFF`（差集）、`SUNION`（并集） |

### 集合运算

```bash
SADD user:1:friends "李四" "王五" "赵六"
SADD user:2:friends "王五" "赵六" "钱七"

SINTER user:1:friends user:2:friends   # → 王五 赵六（共同好友）
SDIFF  user:1:friends user:2:friends   # → 李四（1有2没有）
SUNION user:1:friends user:2:friends   # → 全部去重
```

**典型场景**：共同好友/共同关注（SINTER）、标签去重、抽奖（SPOP）、UV 统计（大数据用 HyperLogLog）。

> 判断"存在性"用 Set（SISMEMBER O(1)），别用 List（遍历 O(N)）。

## Sorted Set（ZSet）

| 要点 | 说明 |
|------|------|
| 元素 + score | 按 score 排序，元素不重复 |
| 底层 | skiplist + hashtable |
| `ZRANGE` | **升序**（从小到大）|
| `ZREVRANGE` | **降序**（从大到小，排行榜常用）|
| `ZINCRBY` | 给某元素分数加减 |

### 为什么用 skiplist 不用红黑树？（超高频面试）

1. **实现简单** —— 跳表代码远比红黑树简单，红黑树旋转逻辑复杂易错
2. **范围查询方便** —— 排行榜取"前 10 名""分数 80~100"，跳表顺链表扫即可；红黑树要中序遍历
3. **并发友好** —— 跳表局部改几个指针，红黑树范围旋转可能波及全局

> 记忆：**简单、范围查询、并发**。

### 排行榜实战

```bash
ZINCRBY game:rank 50 "赵六"              # 赵六 +50 分
ZREVRANGE game:rank 0 9 WITHSCORES       # 取前 10 名（带分数）
```

### 易错点：排名从 0 开始

```bash
ZRANGE key 0 0            # 升序第 0 名 = 分数最低
ZREVRANGE key 0 0         # 降序第 0 名 = 分数最高（冠军）
ZREMRANGEBYRANK key 0 0   # 删分数最低（清垫底数据）
```

> **前 N 名 = `0 (N-1)`**，两端闭区间（类似数组下标）。
> 前 3 名是 `0 2`（3 个），不是 `0 3`（那是 4 个）。
> `-1` 代表倒数第一个（另一端）。

## Key 管理（面试必考）

### 禁止 `KEYS *`

`KEYS *` 复杂度 O(N)，Redis 单线程下会**阻塞所有请求**，几十万 Key 时卡死几秒。

**替代**：`SCAN`（分批返回，不阻塞，游标返回 0 表示扫完）

```bash
SCAN 0                       # 从游标 0 开始
SCAN <next_cursor>           # 用返回的游标继续
SCAN 0 MATCH user:*          # 带 MATCH 过滤
```

**SCAN 的 COUNT 不精确**（易错点）：`COUNT 10` 不保证返回 10 个——按**哈希桶**扫描，可能返回 8 或 12 个。但**确定性**、无随机性。

### DEL vs UNLINK（删大 Key）

| 命令 | 方式 | 适用 |
|------|------|------|
| `DEL key` | **同步**删除，阻塞主线程 | 小 key |
| `UNLINK key` | **异步**删除（后台清理）| **大 Key 推荐** |

> 几百万元素的 Hash/List 用 DEL 会阻塞很久，用 UNLINK 后台清理。

### TTL 三大特殊值（必背）

| 返回值 | 含义 |
|-------|------|
| **`-1`** | key 存在，**永不过期**（没设过期时间）|
| **`-2`** | key **不存在**（从没建过 / 已过期被删）|
| **正数** | 剩余存活秒数 |

### Key 命名规范

```
项目:业务:ID:字段
```

例：`user:1001:profile`、`order:20260720:detail`、`cache:product:500:info`

用**冒号 `:`** 分隔——客户端/可视化工具会自动识别为层级，展示成树状。

### 通用规律：返回"全部"的命令都要警惕大数据

`KEYS *`、`HGETALL`、`SMEMBERS`、`ZRANGE` 全量等，大数据量都会阻塞。分别用 `SCAN`、`HSCAN`、`SSCAN` 替代。

---

## 易错点红榜

1. **大小写**：命令不区分，key 和 value 区分
2. **HDEL vs DEL**：HDEL 删字段（必须带 field），DEL 删整个 key
3. **队列方向**：LPUSH + RPOP 才是 FIFO；LPUSH + LPOP 是栈
4. **返回全部的命令**：HGETALL/SMEMBERS/KEYS 大数据会阻塞 → 用 HSCAN/SSCAN/SCAN
5. **排名从 0 开始**：前 N 名 = `0 (N-1)`，两端闭区间
6. **SCAN COUNT 不精确**：按哈希桶扫描，但确定性无随机性
7. **TTL 的 -2 = 不存在**（不是"没过期"）
