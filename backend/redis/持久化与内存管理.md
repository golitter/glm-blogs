# 持久化与内存管理：重点摘要

---

## 1. RDB 快照

- 某一时刻的**全量二进制快照**，默认文件 `dump.rdb`
- 恢复快、文件小，适合备份、迁移、灾难恢复
- 触发方式：自动（`save` 配置）、`BGSAVE`（推荐）、`SAVE`（阻塞，禁用）

| 配置格式 | 含义 |
|---------|------|
| `save 3600 1` | 1 小时内 ≥1 次变更触发 |
| `save 300 100` | 5 分钟内 ≥100 次变更触发 |
| `save 60 10000` | 1 分钟内 ≥10000 次变更触发 |

- 三条规则是 **OR** 关系，满足任一即触发

### SAVE vs BGSAVE

| 方式 | 是否 fork | 是否阻塞 | 说明 |
|------|----------|---------|------|
| `SAVE` | 否 | **全程序阻塞** | 主进程自己写，禁用 |
| `BGSAVE` | 是 | 仅 fork 短暂阻塞 | 子进程写，主进程继续服务 ⭐ |
| 自动 RDB | 是 | 仅 fork 短暂阻塞 | 内部走 BGSAVE 逻辑 |

> Redis「单线程」指**命令执行路径**单线程，仍可 fork 子进程 / 起后台线程。

### COW（Copy-On-Write）机制

- fork 后父子进程**先共享同一批内存页**，不立即复制
- 主进程修改某页时，OS 才复制那一页（**按页复制**）
- 额外内存开销 ≈ **快照期间被修改的数据量**，不是全部数据
- 子进程始终看到 fork 那一刻的数据，用它生成 RDB；fork 后的新写入**不进本次 RDB**

### RDB 会丢数据吗？

- RDB 文件是**完整的**，只是**可能不够新**
- 只靠 RDB 恢复，会丢**最近一次快照之后**的写入

```text
10:00:00  BGSAVE 生成 dump.rdb
10:00:30  写入 key A
10:01:00  写入 key B
10:01:20  宕机         ← A、B 丢失
```

## 2. AOF 日志

- 逐条记录**写命令**，追加写入，恢复时逐条重放
- 比 RDB 更安全，但恢复慢、文件大（靠重写压缩）

| fsync 策略 | 数据安全 | 性能 | 推荐 |
|-----------|---------|------|------|
| `always` | 最高（几乎不丢） | 最差 | 极端安全 |
| `everysec` | 最多丢 1 秒 | 均衡 | **生产首选** ⭐ |
| `no` | 丢数秒 | 最好 | 可容忍丢失 |

### AOF 重写

- 精简冗余命令，只保留**最终状态**（`SET`→`INCR`×3 压成一条 `SET count 4`）
- fork 子进程执行，不阻塞主线程
- 重写期间新命令**同时写旧文件 + 重写缓冲区**
- 触发：文件比上次重写后增长 **100% 且 ≥64MB**

## 3. 混合持久化（Redis 4.0+）

- AOF 重写时，**前半段 RDB 格式 + 后半段 AOF 增量**
- 开启：`aof-use-rdb-preamble yes`（需先开 AOF）

| 维度 | 纯 RDB | 纯 AOF | 混合 ⭐ |
|------|--------|--------|--------|
| 数据安全 | 丢数分钟 | 丢 ≤1 秒 | 丢 ≤1 秒 |
| 恢复速度 | 最快 | 较慢 | 较快 |
| 文件大小 | 最小 | 较大 | 较小 |

- **AOF 优先级更高**：启动时存在 AOF 则优先用它恢复

```conf
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
```

## 4. 内存淘汰策略

内存达到 `maxmemory` 上限时删谁。两个维度：**范围**（`allkeys-*` / `volatile-*`）× **算法**（`lru` / `lfu` / `random` / `ttl`）。

| 策略 | 行为 | 场景 |
|------|------|------|
| **`allkeys-lru`** | 所有 Key 淘汰最久未用 | **纯缓存首选** ⭐ |
| `allkeys-lfu` | 所有 Key 淘汰频率最低 | 热点明显的缓存 |
| `volatile-lru` | 仅过期 Key 中淘汰最久未用 | 部分数据可淘汰 |
| `volatile-ttl` | 优先淘汰 TTL 最短的 | 快过期数据先走 |
| `noeviction` | 不淘汰，拒绝写入 | 数据不能丢 |

- **LRU**：最近最少使用（按访问时间）；**LFU**：最不经常使用（按访问频率，4.0+）

## 5. 内存优化

小数据用紧凑编码省内存，超阈值自动切高效编码：

| 类型 | 小数据编码 | 转换阈值 |
|------|----------|---------|
| Hash | ziplist / listpack | >512 entries 或 value >64B |
| Set | intset | 非全整数 或 >512 元素 |
| ZSet | ziplist / listpack | >128 entries 或 value >64B |

排查命令：

```redis
OBJECT ENCODING key        # 看底层编码
MEMORY USAGE key           # 看单个 Key 占用
INFO memory                # 看整体内存
```

- `mem_fragmentation_ratio` 理想 **1.0~1.5**；过高→重启/碎片整理，过低→可能用了 swap

## 易错点提醒

- **单线程 ≠ 不能 fork**：单线程指命令执行，持久化/删除靠子进程或后台线程
- **RDB 是完整快照，但可能不够新**；只靠 RDB 会丢最近一段写入
- **`SAVE` 不 fork 会阻塞所有请求，生产禁用**；`BGSAVE` fork 子进程不阻塞
- **`docker restart` ≠ `docker rm`**：restart 不丢数据，rm 后没挂载卷才丢
- **`CONFIG SET` 仅运行时生效**，永久生效需改 `redis.conf`

## 面试速查

| 问题 | 答案 |
|------|------|
| Redis 单线程吗？ | 命令执行路径单线程，仍可 fork 子进程 / 后台线程 |
| RDB vs AOF？ | RDB 全量快照恢复快但可能丢数据；AOF 逐条记录更安全但恢复慢 |
| 生产推荐？ | AOF（everysec）+ 混合持久化 |
| SAVE vs BGSAVE？ | SAVE 不 fork 会阻塞；BGSAVE fork 子进程后台执行 |
| 自动 RDB 怎么触发？ | 多条 `save` 规则 OR 关系，满足任一即触发 |
| COW 原理？ | fork 后共享内存页，修改时才按页复制，开销≈修改量 |
| AOF 重写原理？ | fork 子进程只保留最终状态，新命令同时写旧文件和重写缓冲区 |
| 淘汰策略怎么选？ | 纯缓存 → `allkeys-lru`；数据不能丢 → `noeviction` |
| ziplist 何时转 hashtable？ | Hash >512 entries 或 value >64B（ZSet 是 >128） |
| 碎片率怎么看？ | `INFO memory` → `mem_fragmentation_ratio`，理想 1.0~1.5 |
