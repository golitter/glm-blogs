# 缓存设计：重点摘要

---

## 1. 缓存读写策略

| 策略 | 读流程 | 写流程 | 适用场景 |
|------|--------|--------|----------|
| **Cache Aside（首选）** | 缓存→DB→回填 | 更新 DB → **删除**缓存 | 通用 |
| Read/Write Through | 缓存层代理读写 | 缓存层代理同步 DB | 读多写少 |
| Write Behind | 缓存→DB | 只写缓存，异步刷盘 | 写密集可容忍丢失 |

> **核心原则：删缓存而非更新缓存**。删除是幂等操作（执行一次和多次效果一样），并发下不会出错。更新缓存可能导致先到的请求后更新，旧值覆盖新值。

---

## 2. 缓存三大问题速查

| 问题 | 成因 | 核心方案 | 一句话记忆 |
|------|------|----------|-----------|
| **穿透** | 数据根本不存在 | 空值缓存 + 布隆过滤器 | 不存在的请求挡回去 |
| **击穿** | 单个热点 Key 过期 | 互斥锁 + 热点预加载 | 一个去查，其余等 |
| **雪崩** | 大量 Key 同时过期 | 随机 TTL + 多级缓存 | 过期时间打散 |

---

## 3. 布隆过滤器

- **原理**：key → 多个哈希函数 → 位数组多个位置置 1
- **特性**：说不存在 → **一定不存在**；说存在 → **可能不存在**（误判）
- **不能删除**（把 1 改 0 会影响其他 key）
- **Redis 实现**：通过 RedisBloom 模块（BF.ADD / BF.EXISTS / BF.RESERVE）
- **防穿透用法**：缓存前加一层，不存在的 key 直接拦截，不打 Redis 也不打 DB
- **前提**：需要提前把所有合法 key 加入布隆过滤器（启动预热 + 新增时同步）

---

## 4. 互斥锁防击穿

- **锁实现**：`SET lock:key 1 NX EX 5`（NX 不存在才设，EX 防死锁）
- **流程**：抢到锁的请求查 DB → 写缓存 → 释放锁；没抢到的 sleep → 重试查缓存
- **锁超时时间**：略大于 DB 查询时间（3~5 秒），太短锁提前释放等于没锁

---

## 5. 热点预加载

- **做法**：后台定时任务定期从 DB 查最新数据，更新缓存值并重置 TTL
- **效果**：热点数据永不过期，杜绝击穿
- **注意**：redis-cli 命令只是底层等价操作，实际由应用代码定时任务执行
- **适用范围**：仅限真正的热点数据，不能所有数据都这么搞

---

## 6. 缓存雪崩防护

- **随机 TTL**：基础时间 + 随机偏移（如 30min ± 5min），打散过期时间
- **多级缓存**：L1 本地缓存（Guava/Caffeine）→ L2 Redis → DB
- **高可用**：哨兵/集群防 Redis 宕机
- **熔断降级**：DB 压力大时直接返回默认值

---

## 7. 数据一致性

### 三种方案

| 方案 | 做法 | 一致性 |
|------|------|--------|
| **延迟双删** | 更新 DB → 删缓存 → 延迟 N ms → 再删 | 较强 |
| **Canal 监听 binlog** | MySQL binlog → Canal → 自动删缓存 | 强 |
| **短 TTL 兜底** | 缓存设短过期时间 | 最终一致 |

### 核心原则

- **先更新 DB 再删缓存**（不是先删缓存）
- **延迟双删的延迟时间**：略大于一次"读 DB + 写缓存"的时间，通常 500ms~1s

---

## 面试速查

| 问题 | 答案 |
|------|------|
| Cache Aside 流程？ | 读：缓存→DB→回填；写：更新 DB→删缓存 |
| 为什么删缓存不更新？ | 并发下更新可能旧值覆盖新值，删除是幂等的 |
| 穿透/击穿/雪崩区别？ | 穿透=不存在，击穿=热点过期，雪崩=大面积过期 |
| 布隆过滤器特点？ | 说不存在一定不存在，说存在可能不存在，不能删除 |
| 互斥锁怎么实现？ | SET NX EX，抢到锁的查 DB，其余等待重试 |
| 怎么防雪崩？ | 随机 TTL + 多级缓存 + 高可用 + 熔断降级 |
| 缓存一致性方案？ | 先更新 DB 再删缓存；延迟双删；Canal 监听 binlog；短 TTL 兜底 |

---

## 本阶段易错点

- **幂等操作**：删除缓存是幂等的，重复执行结果一样；更新缓存不是幂等的
- **并发 vs 并行**：并发是交替执行（单核也可），并行是真正同时执行（需多核）
- **布隆过滤器是缓存前的拦截层**，不是缓存本身；需要提前预热合法 key
- **热点预加载是应用代码的定时任务**，不是 redis-cli 命令，redis-cli 只是等价操作示意
- **maxmemory-policy** 需要确认是否正确配置为 `allkeys-lru`（默认是 `noeviction`）
